## Context
Owner's brainstorm, 2026-11-03 (scope card accepted; decision `docs/decisions/2026-11-03-workouts.md`). Workouts were left on the Loop ("Training sessions … are not read in v1", `band-sync.md`), so a ride showed as high heart rate and skipped stress readings, and a low-recovery morning had no reason. The Polar BLE SDK 8.5.0 can switch on automatic training detection and read training sessions; the Loop wakes Vesel with an `exerciseStatus` notice that today only maps to `.checkIn`.

What the SDK gives (read from the checked-out source, `PolarBleSdk` 8.5.0):
- `setAutomaticTrainingDetectionSettings(id, mode:, sensitivity: 0–100, minimumDuration: s)` reads the band's `UDEVSET` and rewrites it with only the training-detection part changed (unlike `setPolarUserDeviceSettings`, which rebuilds it). `getPolarUserDeviceSettings` returns `automaticTrainingDetectionMode`, `…Sensitivity`, `minimumTrainingDurationSeconds`; Polar's defaults are 50 and 600 s (`PolarUserDeviceSettings.toProto`).
- `getTrainingSessionReferences(id, fromDate:, toDate:)` → `[PolarTrainingSessionReference]` (`date`, `path` like `/U/0/20261103/E/071000/TSESS.BPB`, `exercises` with their file types, `fileSize`). `getTrainingSession(id, reference)` → `PolarTrainingSession` with `sessionSummary: Data_PbTrainingSession` and `exercises: [PolarExercise]` (`exerciseSummary` BASE, `samples`, `samplesAdvanced`, `route`, `routeAdvanced`).
- **Gotchas:** `Data_PbTrainingSession`'s fields are public (`start` with `timeZoneOffset`, `duration`, `distance`, `calories`, `heartRate.average/maximum`, `trainingLoad.trainingLoadVal`, `cardioLoad.exerciseLoad`, `cardioLoadInterpretation`, `sport.value`, `startTrigger` manual or automatic). `Data_PbExerciseBase`'s fields are **internal**: read it only through SwiftProtobuf's public `jsonString()`. `Data_PbExerciseSamples.heartRateSamples` and `recordingIntervalMs` are public. `readExercise` uses `try?` per file: a file that fails to read comes back nil, like the other SDK fetches.
- `PolarExerciseSession.ExerciseInfo.parse(from:)` (public) reads the `exerciseStatus` notice's parameters: `status` (`inProgress`, `paused`, `stopped`, …), `sportProfile` (`running` 1, `cycling` 2, `otherOutdoor` 16, else `unknown`), `startTime`.
- The features list in `PolarWearableSource.init` lacks `.feature_polar_training_data`; it must be added.
- No swimming lengths or pool data in the session or exercise summary the SDK exposes (`PbSwimmingPoolInfo` exists only for sport profiles).

## Approach

Workouts are their own small world beside the day-based kinds: they aren't fetched per day, aren't cleared, and have no ledger. A read lists the Loop's training sessions from the day before the newest stored workout (or the day before pairing) through today and reads each one Vesel doesn't have yet, or whose file size changed. Each is stored whole in one transaction: a typed `workout` row plus one `workout_file` row per file as it came off the band (protobuf JSON). The owner's fix lives in `workout_choice`, which a band re-read never touches. The phone's route lives in `workout_route`, recorded by the app while the Loop says a workout runs, and joined to the band's workout by time when read.

Alternatives ruled out: a new `FetchKind` (it would drag workouts into the per-day ledger and `ClearPlan`, which must never clear them); one JSON blob per day in `raw_export` (several workouts a day collide on `(day, kind)`); the fix as columns on `workout` (an upsert could overwrite it; a separate table makes "never overwritten" structural); starting route recording from `observeExerciseStatus` as a second subscription (the existing device-to-host notice already carries the same status, parsed by the SDK's public `ExerciseInfo.parse`).

### Phase 1 — Band and storage (no screens)

**VeselCore** (`Models/Workout.swift`, new):

### Phase 2 — Analysis (VeselCore + stress pass)

- `Analysis/WorkoutLabel.swift`: `WorkoutLabel.make(workout:, choice:, route: WorkoutRouteSummary?, history: [(start: Date, sport: WorkoutSport)], sports: Set<WorkoutSport>, zone:) -> WorkoutLabel` with `sport: WorkoutSport?`, `source: .owner | .band | .speed | .timeOfDay | .none`, `hidden: Bool`. Rules in `docs/how-it-works/workouts.md` (owner's fix → band's sport → speed > 13 km/h with a route → most frequent sport within ±2 h of the start's local time over the 90 days before, counting only `.owner` and `.band` labels → nil, shown "Workout"). Ties: `WorkoutSport.guessOrder`. Only sports in `sports`. Band sport outside `sports` is still shown (it is the band's word).
- `Analysis/WorkoutEffort.swift`: `WorkoutEffort.make(load: Double?, source:) -> WorkoutEffort?` → `.easy` (< 60), `.moderate` (60–149), `.hard` (≥ 150); thresholds in `WorkoutThresholds` (with `guessSpeedKmh = 13`, `guessWindowHours = 2`, `guessHistoryDays = 90`, `routeAccuracyMeters = 25`, `routeMaxHours = 6`). `Explanation` (method `workout`, version 1): the load, its source field, the cut-offs, the sport rule used. Words: "Easy", "Moderate", "Hard".
- `Analysis/WorkoutRouteSummary.swift`: from route points (`time, lat, lon, accuracy`) and the workout window: keep points inside the window with accuracy ≤ 25 m, distance = sum of haversine legs (Earth radius 6 371 008.8 m), average speed = distance ÷ `durationSeconds`. Pure, tested with written-out numbers. (Phase 3 stores the points; phase 2 only needs the type for the label.)
- Stress (`Analysis/Stress.swift`, `stress` version 3): `windows(sessions:heartRates:activityHeartRate:workouts: [DateInterval])` skips a reading that overlaps a workout (no margin beyond the existing 2-minute exercise margin), counted as `StressCounts.duringWorkout`; the explanation adds "N were inside workouts". Workouts passed are the day's non-hidden ones. Version bump recomputes every day once (existing rule).
- `StressInputs.workouts(db, day:)` (VeselStorage): non-hidden workouts overlapping the day. `StressUpdater.touchedDays` adds days with a `workout.stored_at` or `workout_choice.chosen_at` later than that day's `stress.readings` `computed_at` (same shape as the `late` query).
- `Glossary`: two terms, `workout` ("A workout is a stretch your Loop noticed you exercising: …, how the band knows") and `effort` ("Effort is Polar's training load for one workout: …; Vesel shows it as Easy, Moderate or Hard; it is never added up"). `WhatHelps`: nothing.

**Ships alone:** after phase 1. Visible change: stress numbers skip workouts (the Stress page's explanation says so).

## Decisions
1. Workouts are read, shown and explain stress, heart rate and recovery; effort per workout is in; never summed, no bests or streaks (**mine**, 2026-11-03).
2. Vesel switches on automatic training detection; automatic start/stop is the core, no GPS needed (**mine**).
3. Workouts stay on the band: never `deleteTrainingSession` (**mine**).
4. Read on every sync and when the Loop's exercise notice wakes Vesel (**mine**).
5. Phone GPS route from the Loop's start to end, joined to the workout; complete without it; phone + Mac only (**mine**).
6. Screens: Journal cards between night and day; Today line and headline naming yesterday's workout; purple blocks on heart-rate and stress charts; Workout page; Body nothing (**mine**).
7. Stress readings inside a workout aren't counted (**mine**).
8. Settings: your sports (all on), notice by itself (on), sensitivity, shortest workout (10 min), record my route; band first then phone (**mine**).
9. Sport label order: band → speed → time of day → "Workout"; owner's sports only; fix sheet with "Not a workout"; the fix is never overwritten (**mine**).
10. Purple #7A4FD6 / #B79BFF for workouts (**mine**; contrast checked by the agent: 4.8:1 on the light background, 5.4:1 on white, 8.4:1 dark).
11. Out of scope: trimming, starting from the app, weekly totals, Body (**mine**).
12. "Record my route" on by default; permission asked when Workouts settings first open or the switch is turned on (**agent's, assumed**; hard to undo only in that the first ask is spent).
13. Route drawn on Apple's map (MapKit); map pictures of the area come from Apple; no geocoding (**agent's, assumed**; touches the no-cloud rule for location, so the owner confirms).
14. Effort cut-offs: Easy < 60, Moderate 60–149, Hard ≥ 150 on Polar's cardio load (else training load); provisional (**agent's, assumed**).
15. Storage shape: `workout` keyed by band start, raw files in `workout_file`, the fix in its own `workout_choice`, route in `workout_route`; all backed up; no new `FetchKind`, no ledger (**agent's**; hard to undo: migrations).
16. Workouts are read between skin temperature and heart rate; not a row in the reading list (**agent's**).
17. A workout the band reports as running isn't read; an incomplete one is stored and read again (**agent's**).
18. One-time switch-on: only when Vesel never set it; keeps the band's own sensitivity and minimum (**agent's**).
19. Distance and speed only from the phone's route; the band's distance is stored but not shown (**agent's**).
20. Headline names only a Moderate or Hard workout from yesterday, the highest-load one (**agent's**).
21. Workouts settings is a pushed screen from one Loop & settings row, in its own section, so it never collides with the wrist choice's "Worn on" row (**agent's**).
22. Swimming: build the time + heart rate case; distance and pool length only after the real-Loop check, as a later brief (**agent's**).
23. A workout belongs to the day it started (**agent's**).
