**Date**: 2026-11-03
**Status**: Approved (2026-11-03, after plan review)

## TL;DR
- Seven phases, one PR each, inner layers first: 1 storage, 2 band reading, 3 analysis, 4 settings, 5 route, 6 Workout page + Journal, 7 Today + chart blocks.
- Phase 1: migration adds `workout`, `workout_file`, `workout_choice`, keyed by the band's session folder (`20261103/071000`); all backed up.
- Phase 2: every read lists all training sessions on the Loop and reads new or changed ones, between skin temperature and heart rate.
- Phase 2: the Loop's `getExerciseStatus` decides which session is still running; one failing session never stops the read.
- Phase 2: Vesel switches the Loop's automatic training detection on once, keeping the Loop's own values. Never `deleteTrainingSession`.
- Phase 3: VeselCore `WorkoutLabel` (sport guess), `WorkoutLoad` (Polar's cardio load and its own word), stress skips workout windows (`stress` v3).
- Phase 4: Workouts settings screen; band settings save band first, then phone.
- Phase 5: `RouteRecorder` records phone GPS from the Loop's start to end notice; `workout_route` migration; location strings.
- Phase 6: Workout page (route on Apple's map, heart rate, cardio load, calories), fix sheet, Journal Workouts section.
- Phase 7: Today's workout lines, `headline` v4 names yesterday's workout, purple blocks on heart-rate and stress charts.
- Route on Apple's map (MapKit): only tiles for the area are fetched; offline, the map's grid with the route still drawn.
- Location is asked only on a tap: "Record my route" shows "Needs location · Allow" until allowed.
- New data colour: workout purple #7A4FD6 / #B79BFF (4.8:1 and 8.4:1 on the background).
- Load = Polar's cardio load number, Polar's word beside it once confirmed; no Vesel-made word.
- Risk areas: two migrations, health and location data to the Mac backup (existing pinned path only), Apple's map tiles, a new band write.

## Context
Owner's brainstorm, 2026-11-03 (scope card accepted; decision `docs/decisions/2026-11-03-workouts.md`). Workouts were left on the Loop ("Training sessions … are not read in v1", `band-sync.md`), so a ride showed as high heart rate and skipped stress readings, and a low-recovery morning had no reason. The Polar BLE SDK 8.5.0 can switch on automatic training detection and read training sessions; the Loop wakes Vesel with an `exerciseStatus` notice that today only maps to `.checkIn`.

What the SDK gives (read from the checked-out source, `PolarBleSdk` 8.5.0):
- `setAutomaticTrainingDetectionSettings(_ identifier:, mode:, sensitivity: 0–100, minimumDuration: s)` (needs `feature_polar_device_control`, already on) reads the band's `UDEVSET` and rewrites it with only the training-detection part changed (unlike `setPolarUserDeviceSettings`, which rebuilds it). `getPolarUserDeviceSettings(identifier:)` returns `automaticTrainingDetectionMode`, `automaticTrainingDetectionSensitivity`, `minimumTrainingDurationSeconds`. When the Loop has none, the SDK's own fallback is 50 and 600 s (`PolarUserDeviceSettings.toProto`).
- `getTrainingSessionReferences(identifier:fromDate:toDate:)` walks every day folder under `/U/0/` whatever the dates (nil = no bound) and returns `[PolarTrainingSessionReference]`: `date`, `path` (`/U/0/20261103/E/071000/TSESS.BPB`), `trainingDataTypes`, `exercises` (each with `exerciseDataTypes`), `fileSize`. `getTrainingSession(identifier:trainingSessionReference:)` → `PolarTrainingSession`: `sessionSummary: Data_PbTrainingSession`, `exercises: [PolarExercise]` (`exerciseSummary`, `samples`, `samplesAdvanced`, `route`, `routeAdvanced`).
- `getExerciseStatus(identifier:)` (public) → `PolarExerciseSession.ExerciseInfo`: `status` (`notStarted`, `inProgress`, `paused`, `stopped`, `syncRequired`), `sportProfile`, `startTime?`. `ExerciseInfo.parse(from:)` reads the same thing from the `exerciseStatus` notice's parameters.
- **Gotchas:**
  - A file whose **transfer** fails throws, and the whole `getTrainingSession` throws (`PolarTrainingSessionUtils.readTrainingSession`, `readExercise`). Only a file that arrives but doesn't **parse** comes back nil (`try?`).
  - `Data_PbTrainingSession`'s values are public (`start` with `timeZoneOffset` minutes, `duration`, `calories`, `heartRate.average/maximum`, `trainingLoad.trainingLoadVal`, `cardioLoad.exerciseLoad`, `cardioLoadInterpretation` (1–5, "comparison of cardio load to 90 day average", very low … very high per the proto comment), `sport.value`), but their `has…` presence checks are internal: a missing value reads as 0. `Data_PbExerciseBase`'s fields are internal altogether. `Data_PbExerciseSamples` has public `recordingInterval: PbDuration` and `heartRateSamples`.
  - Every message's `serializedData()` is public (SwiftProtobuf); `.GZB` files arrive already unzipped.
- The features list in `PolarWearableSource.init` lacks `.feature_polar_training_data`; it must be added.
- Sport ids the SDK names: `0` unknown, `1` running, `2` cycling, `16` other outdoor. Nothing else is known until the real Loop is read.
- No swimming lengths or pool data in what the SDK exposes (`PbSwimmingPoolInfo` exists only for sport profiles).

## Approach

Workouts are their own small world beside the day-based kinds: they aren't fetched per day, aren't cleared, and have no ledger. Each Loop session is named by its folder on the band, `session = "20261103/071000"` (from the reference's path), which never changes for that session; every workout table is keyed by it. A read lists all sessions on the Loop and reads each one Vesel doesn't have, or whose total file size changed. Each is stored whole in one transaction: a typed `workout` row plus one `workout_file` row per file, kept as the SDK handed it over (`serializedData()`, unknown fields included). The owner's fix lives in `workout_choice`, which a band read never touches. The phone's route lives in `workout_route`, recorded by the app while the Loop says a workout runs and joined to the band's workout by time.

Ruled out: a new `FetchKind` (drags workouts into the per-day ledger and `ClearPlan`, which must never clear them); `raw_export` (several workouts a day collide on `(day, kind)`); keying on the parsed start time (a re-read giving another start would collide with the unique path and fail every sync); the fix as columns on `workout` (an upsert could overwrite it); in-memory "workout running" state from events (lost on relaunch, stuck when an end notice is missed: `getExerciseStatus` asks the Loop instead); `jsonString()` as the raw copy (drops unknown fields); a plain line drawn without a map (owner chose the map); Vesel-made effort words (owner chose Polar's own number and word).

### Phase 2 — Reading workouts from the Loop (VeselWearable, app wake handler)

- `WearableSource` gains: `workoutDetection() async throws -> WorkoutDetection?` (nil when the Loop has none), `setWorkoutDetection(_:) async throws`, `workoutStatus() async throws -> WorkoutStatus` (`running(since: Date?)` or `notRunning`), `workoutReferences() async throws -> [WorkoutReference]` (`session`, `date`, `fileSize`, `fileNames`), `workout(_ reference:) async throws -> BandWorkout`.
- `BandEvent` gains `.workoutStarted(at: Date)` and `.workoutEnded(at: Date)`, parsed by `PolarBandEvents.event` with `ExerciseInfo.parse(from: parameters)`: `inProgress` → started (`startTime ?? now`), `stopped` → ended (now); `paused`, others or unreadable → `.checkIn`. Events are only for the route recorder (phase 5) and the check-in read; reading never depends on them.
- `PolarWearableSource`: add `.feature_polar_training_data`; implement the calls. `workoutReferences()` = `getTrainingSessionReferences(identifier:fromDate: nil, toDate: nil)`. `workout(_:)` = `getTrainingSession(identifier:trainingSessionReference:)` then `PolarMapping.workout(_:)`:
  - `session` from the path; `start` from `sessionSummary.start` with its `timeZoneOffset`; a 0 offset with the phone's zone not at UTC reads the start in the phone's zone. Duration from `PbDuration`.
  - **0 means absent** (presence checks are internal): calories, loads, heart rates of 0 become nil. `cardioLoad.exerciseLoad`, `cardioLoadInterpretation` (1–5; anything else nil) and `trainingLoad.trainingLoadVal` each stored as given (0 → nil). Non-finite numbers dropped as in the other mappers.
  - Heart rates from the first exercise's `samples.heartRateSamples` at `recordingInterval` (`PbDuration` → ms); none when the interval is 0 or there are no samples.
  - Files: `serializedData()` of the session summary and, per exercise, BASE, SAMPLES, SAMPLES2, ROUTE, ROUTE2 when present. A file the reference lists but that came back nil goes into `unreadableFiles`. A summary with no duration is not a finished workout: `workout(_:)` throws `WorkoutReadError.unfinished`.
  - Add the `SwiftProtobuf` product to the VeselWearable target (the package already pins it).
- `BandSync`:
  - `setWorkoutDetection(_:)` like `firstTimeUse`: `exclusively`, pause live, write, resume (also on failure).
  - One-time switch-on, at the start of a read's band session (after the clock is set): if `workouts.detectionSetUp` is absent, read `workoutDetection()`; write `isOn: true` with the Loop's own sensitivity and minimum when it has them, else `sdkFallback`; then store `workouts.detection` and `workouts.detectionSetUp`. A failure leaves the key absent and the read carries on; the next read tries again.
  - `fetchWorkouts()` runs after `.skinTemperature` and before `.heartRate` in `fetchStoreAndClear` (the kinds array is unchanged; the loop calls it between them):
    1. `status = try? workoutStatus()`; on `running(since:)`, skip references dated at or after `since − 60 s` (since nil: references from the last 6 hours not yet stored). Unknown status: read everything (an unfinished one throws `unfinished` and is skipped).
    2. `references = workoutReferences()` with `limits.backlogCall` (it walks every folder) and `answered`.
    3. Read each reference whose session isn't stored or whose `fileSize` differs, one at a time (`call { }`, 90 s). Each is caught on its own: a throw (`unfinished`, a failed transfer) skips that session and the read carries on to heart rate; a failed transfer is tried again on the next read, at most once an hour per session (in memory). Stored with `database.save(_:storedAt:)`.
    4. A stored workout with `unreadableFiles` is not read again unless its `fileSize` changes (a parse failure repeats).
    Workouts are never in the clear step: they have no `StoredDataType`.
  - `SyncStep` is unchanged: workouts aren't a row in the reading list.
- `FakeWearableSource`: workouts per scenario, detection and status held in memory, `-VeselFakeFailure workoutDetection` refuses the write, `-VeselFakeFailure workoutTransfer` throws for one session. `normal`: a 42-minute morning run today (sport 1, load 87), an unlabelled 75-minute evening ride yesterday (load 182). Fixtures from `ios/Tools/make-fixtures.swift` (new `workouts.json`), never hand-edited. `FakeScenario.workoutRunning` reports `running` and emits `.workoutStarted` 5 s after launch and `.workoutEnded` 120 s later (phase 5's Simulator check).
- App, `BandWakeHandler`: `.workoutStarted` / `.workoutEnded` go into the queue as a check-in read (`pipeline.run(.bandCheckIn, onlyIfDue: true)`). Phase 5 adds the recorder beside the queue.
- Loop & settings' storage warning: "Training sessions … aren't read" becomes "Vesel keeps your workouts on the Loop and doesn't read sleep scores and skin-contact files yet, so they stay on the band."

**Ships after 1.** Workouts are read and backed up; nothing new shows. Detection is switched on.

### Phase 3 — Analysis (VeselCore + the stress pass)

- `Analysis/WorkoutThresholds.swift`: `guessSpeedKmh = 13`, `guessWindowHours = 2`, `guessHistoryDays = 90`, `routeAccuracyMeters = 25`, `routeMaxHours = 6`, `routeMinCoverage = 0.5`, `routePointSeconds = 5`.
- `Analysis/WorkoutRouteSummary.swift`: from route points (`time, lat, lon, accuracy`) and the workout window: keep points inside the window with accuracy ≤ 25 m; distance = sum of haversine legs (Earth radius 6 371 008.8 m); covered time = last kept point − first; average speed = distance ÷ covered time; `coverage = covered ÷ durationSeconds`. Tested with written-out numbers, including a route that starts 20 minutes late.
- `Analysis/WorkoutLabel.swift`: `WorkoutLabel.make(workout:, choice:, route: WorkoutRouteSummary?, history: [(start: Date, sport: WorkoutSport)], sports: Set<WorkoutSport>, zone:)` → `sport: WorkoutSport?`, `source: .owner | .band | .speed | .timeOfDay | .none`, `hidden`. Order: owner's choice → `WorkoutSport(bandSportId:)` → with a route whose coverage ≥ 50 %: average speed > 13 km/h cycling, else running → the most frequent sport among owner- or band-labelled workouts starting within ±2 h of this start's local time over the 90 days before → nil ("Workout"). Ties by `guessOrder`; guesses only among `sports`; a band sport outside `sports` still shows.
- `Analysis/WorkoutLoad.swift`: `WorkoutLoad.make(workout)` → `number`, `source` (`.cardioLoad` or `.trainingLoad` when cardio load is absent), `polarWord: String?`. `PolarLoadWord.confirmed: [Int: String]` starts **empty** and gains a rating only after the owner check on the real Loop (the proto comment's very low, low, medium, high, very high are the expected words, not shown until confirmed). `Explanation` (method `workout`, version 1): the load number and its source field, Polar's rating as given, the sport rule used, route coverage. No cut-offs, no Vesel word.
- Stress (`Analysis/Stress.swift`, `stress` version 3): `windows(sessions:heartRates:activityHeartRate:workouts: [DateInterval])` skips a reading that overlaps a non-hidden workout, counted as `StressCounts.duringWorkout`; the explanation adds "N were inside workouts". The version bump recomputes every day once (existing rule).
- VeselStorage: `StressInputs.workouts(db, day:)` (non-hidden workouts overlapping the day). `StressUpdater.touchedDays` adds days whose `MAX(workout.stored_at, workout_choice.chosen_at)` is later than the day's `stress.readings` `computed_at`; the `computed_at` bump after a recompute uses the latest of the ledger's `stored_at` and those two, so a recompute that doesn't change the numbers is not picked again.
- `Glossary`: `workout` and `cardioLoad` (Polar's load for one workout from heart rate and time, compared by Polar with your last 90 days; not added up by Vesel).

**Ships after 2.** Visible: stress numbers skip workouts; the Stress page's explanation says so.

### Phase 5 — Route recording (phone GPS)

- VeselStorage migration (next free `vN`): `CREATE TABLE workout_route (started_at INTEGER PRIMARY KEY, ended_at INTEGER, points_json TEXT NOT NULL, updated_at INTEGER NOT NULL, uploaded_at INTEGER)`; `updated_at` is bookkeeping. `UploadTable.workoutRoute` (key `started_at`). `routes(overlapping: DateInterval)`; a route joins the workout it overlaps most. Points are kept one per 5 s and a route stops after 6 h, so a row stays under about 0.5 MB, far below the 4 MB batch cap.
- `ios/Vesel/Background/RouteRecorder.swift` (app, `@MainActor`): `start(at:)` / `stop(at:)`; `CLLocationUpdate.liveUpdates(.fitness)` with a `CLBackgroundActivitySession`; points in memory, written every 60 s and at stop, each write inside its own `BackgroundTime.begin("Route", database:)` (the database is resumed for it and suspended after; a write that finds it paused waits for the next one). Stops by itself after 6 h. Runs only when `workouts.route` is on (absent = on) and location is allowed. With "Always" it can start from the Loop's notice in the background; with "While using" it starts only while Vesel is open, then the background activity session keeps it going. Never logs a location.
- `BandWakeHandler`: `.workoutStarted(at)` → `routeRecorder.start(at:)` and `.workoutEnded(at)` → `routeRecorder.stop(at:)` in the `listening` task, beside the queue (like the stand-up reminder), so a running read never delays them; the check-in read still goes through the queue.
- `LocationPermission` (app) and the route row in Workouts settings: "Record my route" (toggle, on). While location isn't allowed the row shows "Needs location · Allow"; only a tap on Allow (or turning the switch on) asks iOS: When In Use, then Always. Denied: "Location is off for Vesel in iOS Settings" with Open Settings. Opening a screen never asks.
- `ios/project.yml`: `UIBackgroundModes` + `location`; `INFOPLIST_KEY_NSLocationWhenInUseUsageDescription` "Vesel records your route during a workout your Loop noticed. It stays on your phone and your Mac." and `INFOPLIST_KEY_NSLocationAlwaysAndWhenInUseUsageDescription` "Your Loop starts workouts by itself, so Vesel needs location in the background to record the route. Only during a workout; it stays on your phone and your Mac."

## Decisions
1. Workouts are read, shown and explain stress, heart rate and recovery; each workout's own load is in; not summed over days or weeks for now (`docs/ideas/training-load-trends.md`), no bests or streaks (**mine**, 2026-11-03).
2. Vesel switches on automatic training detection; automatic start and stop is the core, no GPS needed (**mine**).
3. Workouts stay on the band: never `deleteTrainingSession` (**mine**).
4. Read on every sync and when the Loop's exercise notice wakes Vesel (**mine**).
5. Phone GPS route from the Loop's start to end, joined to the workout; complete without it; phone + Mac only (**mine**).
6. Screens: Journal cards between night and day; Today line and headline naming yesterday's workout; purple blocks on heart-rate and stress charts; Workout page; Body nothing (**mine**).
7. Stress readings inside a workout aren't counted (**mine**).
8. Settings: your sports (all on), notice by itself (on), sensitivity, shortest workout (10 min), record my route; band first then phone (**mine**).
9. Sport label order band → speed → time of day → "Workout"; owner's sports only; fix sheet with "Not a workout"; the fix is never overwritten (**mine**).
10. Purple #7A4FD6 / #B79BFF (**mine**; contrast checked: 4.8:1 on the light background, 5.4:1 on white, 8.4:1 dark).
11. Out of scope: trimming, starting from the app, weekly totals, Body (**mine**).
12. "Record my route" is on by default, but iOS asks only when the owner taps Allow (or turns the switch on); the row shows "Needs location · Allow" until then (**main thread on the owner's behalf, 2026-11-03**).
13. The route is shown on Apple's map (MapKit); only the area's tiles are fetched from Apple; offline the map's grid with the route still drawn, no second renderer (**mine**, 2026-11-03; `docs/decisions/2026-11-03-route-map.md`).
14. Load is Polar's cardio load number, with Polar's own word from its rating (1–5) beside it only for ratings confirmed on the real Loop; training load is the labelled fallback only without a cardio load; no Vesel-made word, no cut-offs (**mine**, 2026-11-03).
15. Storage: every workout table keyed by the band's session folder; raw files as the SDK's bytes in `workout_file`; the fix in `workout_choice`; route in `workout_route`; all backed up; no `FetchKind`, no ledger (**agent's**; hard to undo: migrations).
16. Workouts are read between skin temperature and heart rate, listed in full each read, and aren't a row in the reading list (**agent's**).
17. Which session is still running comes from asking the Loop (`getExerciseStatus`), not from remembered events (**agent's**).
18. A session that fails is skipped without stopping the read; a parse failure is kept as unreadable and not re-read until the band's file size changes (**agent's**).
19. One-time switch-on keeps the Loop's own sensitivity and minimum; Forget this Loop resets it (**agent's**).
20. Distance from the phone's route; speed over the time the route covers, shown and used for guessing only with ≥ 50 % coverage; the band's distance stays in its raw file (**agent's**).
21. The headline names yesterday's workout only when Polar rated it 3 or higher of 5 (its middle level or above), the highest cardio load among those; without a rating, none is named; the sentence carries no effort word (**agent's**, on the owner's new basis).
22. Workouts settings is a pushed screen from one Loop & settings row in its own section, so it never collides with the wrist choice's "Worn on" row (**agent's**).
