Vesel Backup, a menu bar app for your Mac

A small icon at the top of your MacBook's screen. It runs the backup, shows that it's working, and pairs your iPhone without Terminal. The 2014 Mac mini keeps the Terminal set-up; both pair the same way.

How it works

What you get

Open Vesel Backup once from Applications. Pair your iPhone from the menu. From then on it opens when you log in and the icon tells you if it's on, off or stuck.

Your answer, recorded

Both ways stay

MacBook: the app. 2014 Mac mini: the Terminal set-up, unchanged. Both make the pairing code with the same script, so the iPhone works with either.

Pairing again means a new code

Your Mac keeps only a fingerprint of the key, so the old code can't be shown twice. Pair again gives a new code; your iPhone scans it and nothing is sent twice.

I assumed

One Mac runs one way, never both; the app steps aside if it finds the Terminal set-up. uv stays installed on your MacBook (it is now). The phone keeps saying "Mac mini".

Decisions
  1. Yours On the MacBook (and any newer Mac) the menu bar app runs the backup while it's open, and opens at login. Replaces "starts at boot" there only.
  2. Yours The menu shows on/off and status, last backup and counts, Pair phone with the code on screen, and Open at login.
  3. Yours Keep both ways: the Terminal set-up stays for the 2014 Mac mini, headless. Same code, same folder; the app explains a Terminal set-up it finds.
  4. Mine Hard to undo: one script makes the certificate and key for both ways; the app carries it and runs it. Tested against the written rules with both versions of the Mac's encryption tool.
  5. Mine The server travels inside the app; uv gives it Python. Without uv the menu says what to install.
  6. Mine Every pairing in the app makes a new key; the certificate stays, so nothing is re-sent.
  7. Mine The pairing code is shown on screen only, never saved.
  8. Mine Counts are read straight from the backup file; the phone's upload format doesn't change.
  9. Mine If the Terminal set-up is installed on the same Mac, the app starts nothing and doesn't pair; the README says how to switch.
Risks
  1. Certificate and key (phone ↔ Mac link). Made by the same script on both Macs and checked in tests; files readable only by you; the key stored only as a fingerprint.
  2. Secrets. The pairing code never touches disk, logs or the clipboard; logs hold only method, path, status and row count.
  3. The server only runs while you're logged in and the Mac is awake. The phone waits and catches up; nothing is lost.
  4. When the MacBook is on another Wi-Fi with the server on, the port is visible there too. Every request needs the key and the link is encrypted; switch it off if you like.
  5. The first start needs internet once to fetch Python's parts (no health data).
  6. Both ways on one Mac would fight over the backup port. The app checks for the Terminal set-up and steps aside.
How we'll know it works
  1. All tests pass, the Mac app builds, the server tests still pass, and a new test checks the pairing script on both encryption tools.
  2. On this Mac with a test folder: pair, scan into the iPhone Simulator, rows arrive, counts show up; pair again and the old key is refused.
  3. Every menu state is screenshotted, including "Terminal set-up found"; file permissions and logs are checked for leaks.
  4. Quit and off really stop the server; a crash leaves no second copy running.
  5. You: install it, pair your real iPhone at home, see "Last backup" update after a sync.
  6. You: log out and in: it opens by itself and is on.
  7. You, later: on the Mac mini, the Terminal steps as written today.
